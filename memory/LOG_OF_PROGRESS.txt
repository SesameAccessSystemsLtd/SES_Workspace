Graphify Deployment Pivot: 
The core problem: if Hermes goes to a VPS, it can't read C:\Users\GilesHugo\.openclaw\workspace\graph\. Local Windows paths break the moment you leave the machine.

So three questions collapse into one: what is the unit of deployment for Hermes?

---
Where memory and graph should live

Right now (OpenClaw, local):
.openclaw/workspace/        ← skills, memory, DB, graph (planned)
.openclaw/agents/*/memory/  ← per-agent memory

The problem with keeping this as the home:
Hermes on VPS has no filesystem access to C:\Users\GilesHugo\. Every script path, every memory read, every graph query breaks. VPS runs Linux — C:\ doesn't exist.

The answer: SES_Workspace (from the architecture we designed) is exactly the thing that gets deployed to the VPS. It's harness-agnostic for this precise reason. When Hermes moves to VPS, you rsync SES_Workspace/ to /opt/ses/workspace/ on the server. Scripts get one path-config change. Memory, graph, skills — all travel together.

Local machine (Windows)                  VPS (Linux)
─────────────────────────────            ─────────────────────────
SES_Workspace\                           /opt/ses/workspace/
  _copilot\graph\         ──sync──>        _copilot/graph/
  skills\                 ──sync──>        skills/
  memory\                 ──sync──>        memory/   (or VPS-native)
  db\ops.db               ──sync──>        db/ops.db
  .env                    ──secure──>      .env (separate secret)

.openclaw/ stays on Windows forever — it's the harness config, not the payload. It doesn't travel.

---
The _copilot/ insight is exactly right

The earlier analysis nailed it: _copilot/ was planned but never created. Graphify's graph.json outputs ARE what _copilot/ was meant to hold. Put them there — inside SES_Workspace, not inside .openclaw/.

SES_Workspace/
└── _copilot/
    ├── graph/
    │   ├── openclaw/graph.json      ← indexed from .openclaw codebase
    │   ├── ses_workspace/graph.json ← indexed from SES_Workspace itself
    │   └── ses_brain/graph.json     ← indexed from SES_Brain vault
    ├── SYSTEM_MANIFEST.yaml         ← what exists, what runs, what's healthy
    ├── PATH_CONFIG.yaml             ← environment-aware paths (local vs VPS)
    └── SKILLS_INDEX.yaml            ← machine-readable skill registry

Any harness on any machine reads _copilot/graph/ instead of crawling raw files. This is the token-saving mechanism.

---
The path problem (biggest practical blocker)

Every script in .openclaw/workspace/skills/ currently has paths like:

load_dotenv(r'C:\Users\GilesHugo\.openclaw\.env')
OUTPUT_PATH = r"C:\Users\GilesHugo\.openclaw\workspace\data\raw_purchasing_emails.json"

These are dead on Linux. The migration to SES_Workspace isn't just copying files — it's replacing hardcoded paths with a PATH_CONFIG.yaml that each script reads at startup.

# SES_Workspace/_copilot/PATH_CONFIG.yaml
workspace_root: C:\Users\GilesHugo\SES_Workspace     # local Windows
# workspace_root: /opt/ses/workspace                  # VPS Linux — swap this line

env_file: C:\Users\GilesHugo\.openclaw\.env          # credentials location
db_ops: ${workspace_root}/db/ops.db
data_dir: ${workspace_root}/data/email_pipeline
requests_dir: ${workspace_root}/queues/REQUESTS

Scripts import one config object instead of 30 hardcoded strings. Swap workspace_root → everything moves.
