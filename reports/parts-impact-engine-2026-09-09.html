Four defects were holding the parts-to-production picture shut. All four are fixed and verified against live data. On top of them sits a forecast that shows production impact before lasercut lands, and an improvement loop that finds friction, stages an action, and only closes it when a metric actually moves.

3 · One missing bind parameter killed the ordering loop Fixed

This is the unnoticed break. db_writer.write_ordering_edge_case() built a named-parameter INSERT including :asana_edge_case_gid, and every caller omitted that key. So the moment either ordering script hit an edge case — the commonest being a blank vendor — it raised sqlite3.ProgrammingError and aborted mid-loop.

Three consequences, all confirmed: the nightly Ordering — Audit Parts Control Routing job has been exiting 1 every night; create_order_tasks.py stopped creating order tasks at the first fallback vendor, which is why nothing has moved to ordered since 3 July; and ordering_edge_cases has stood at zero rows since it was created, so the edge-case channel you asked me to build on has never once received an input.

Fix: optional columns default to NULL inside the writer. Regression test: the exact call shape that raised now returns {'written': 1, 'skipped': 0, 'errors': 0}. The routing audit runs clean and reports 7 items it would add.

4 · The pack reference column held names, not IDs Fixed

Asana reference fields return the referenced task's name. build_assembly_pack_gid was being filled with strings like 1037.1014.N.GateMechanism. — 1,470 of 1,519 populated rows held a name in a column named for an ID, while 44 held a real GID written by a different code path. Two namespaces in one column is why pack association looked 45% broken.

Fix: the name is stored honestly in build_pack_ref_name; the resolver in impact_engine.py matches it against build_assembly_packs.pack_name to recover the real GID. Result: 1,470 parts now carry association_status = 'linked_by_name' with a genuine pack GID.

5 · Production readiness was hardcoded to null Fixed

sync_build_schedule.py wrote "parts_readiness": None and "stage_of_production": None literally, on all 2,618 pack rows. The fields exist and are populated in Asana.

02

Seeing impact before lasercut lands

You said production dates are usually not set until the lasercut order arrives, because that is when packs get built and impact gets assessed — and that this is too late. The engine treats the missing date as the problem to solve rather than a blocker.

impact_engine.py writes one production_impact row per live pack per run. Where Asana has a due date it uses it. Where it does not, it forecasts one, and records which of the two it used so nobody mistakes a forecast for a commitment.

How a pack gets a date
asana — the pack already has a due date
Used as-is. 51 of 71 live packs today.
forecast_lasercut — no date, but lasercut parts exist
Takes the latest ETA across parts routed to lasercut and adds the build lead time. This is the case your question is about: it produces a working production date the moment the lasercut order is placed, not when it is delivered.
forecast_longlead — no date, no lasercut
Falls back to the longest-lead outstanding part plus build lead time.
none — nothing to forecast from
Reported honestly as undated rather than guessed. 20 packs today.

Two assumptions you should set, not me

BUILD_LEAD_DAYS = 10 — working days between lasercut delivery and the pack being needed on the floor. ROUTE_LEAD_DAYS — assumed lead time per supply route when no order exists yet (lasercut 10, subcon 12, buy 14, inhouse 5). Both sit at the top of impact_engine.py as named constants with comments. Every forecast in the system moves when you change them. Days for delivery exists as an Asana field and is populated on zero orders — if it were filled, the engine would use the real per-order figure instead of the route default.

03

The improvement engine

improvement_engine.py runs the loop you asked for: find friction, cluster it, stage an action against a named metric, then refuse to close the case until that metric has actually moved and held. The same machinery validates the amendments in this document, which is the point — it is not a separate reporting layer, it is the test harness for the changes.

Harvest — 15 independent sources
Ordering edge cases, vendor repairs seen in the change stream, vendor spelling collisions, vendor-field misuse, unlinked parts, unassociated parts, unassessed lasercut scope, orders with no delivery date, unsent chase drafts, stale queue lines, vendors with no email, failing cron jobs, unmatched email approvals, revisions changed after ordering, and blocked packs. Each is failure-isolated: a broken harvester cannot stop the run.
Cluster — one case per signature
243 vendor collisions are one case with 243 observations, not 243 cases. Standing backlogs report their current size; discrete events accumulate. Verified stable across consecutive runs — the score does not inflate just because the backlog was counted again.
Score — occurrences × category weight × recency
Weight reflects how much future work a category creates. Recency uses a 30-day half-life, so a problem that stopped happening fades instead of sitting at the top forever.
Stage — record the decision and capture the baseline
You name the action, its type (eliminate / simplify / automate / delegate / retain), the owner, the metric it should move, and the target. The current metric value is snapshotted as the baseline at that moment.
Validate — proven only on evidence
A case becomes proven only if the metric reached target and every reading since staging held it, for at least 14 days. If it has been long enough and the metric has not moved, the case is marked NOT WORKING with the numbers attached. Nothing closes on assertion.

04

Automatic PO numbers, without slowing the desk

You are open to automatic numbering provided it is fast, because orders are processed quickly. The design is reserve now, confirm later: allocation is a single local SQLite transaction with no network call, so it returns instantly. Nothing waits on Asana.

StepWhat happensSpeed
--reserveTakes the next number under an IMMEDIATE lock and prints it. Two people reserving at the same instant cannot collide.local, no network
--confirmAttaches the number to the Asana order task once that task existswhenever
--voidReturns an unused number to the record with a reason, so gaps are explainedwhenever
--statusLast issued, next number, and any reservation over 48h old with no order attachedinstant

Why it needs its own counter, and one thing only you can do

procurement_tasks.po_number holds 933 distinct five-digit prefixes across 1,529 rows, because supplier order refs and invoice numbers have been typed into the same field. "Max + 1" over that column would hand out a number in the 29,000s. The ledger therefore keeps its own counter and must be seeded once from the real PO book: python po_number_allocator.py --seed <last issued number>. It refuses to seed backwards. I have deliberately not guessed the number.
