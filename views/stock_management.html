The Problem Space

🧩

Part Number Ambiguity

Every job prefixes part numbers with a 4-digit job code (e.g. 1566.1003.B.087). The same physical stock item has a different identifier on every project BOM, making automated matching inherently fragile.

📦

Pick vs. Order Routing

Each BOM line must be correctly routed: PICK from KANBAN if in stock, or ORDER if not. A wrong routing wastes stock or delays the job. The decision requires live stock data AND a curated matching index.

🔄

Kitting & Task State

Once tasks are in Asana, their status must update as picking happens, orders arrive, and builds progress. Custom fields, automation rules, and human picks must all stay in sync — across 100+ projects.

🧠

Human Input Reliability

Critical decisions (override quantities, new part mappings, order approvals) must come from Giles with full context. The system must surface exactly the right information at each checkpoint — not drown in noise.

📧

Order Control & Purchasing

Supplier emails, delivery notes, and order acknowledgements arrive unstructured. Matching them to Asana tasks — and updating custom fields correctly — was entirely manual before the purchasing pipeline was built.

⚙️

Automation Reliability

Native Asana rules and Flowsana handle the cross-project logic mesh, but they are fragile: no 24/7 reliability, no audit trail, no ability to handle complex conditions. They break silently when fields change.

BOM Import Pipeline (MRP)

✅ Live

Every job begins with a vendor BOM. This 5-stage pipeline takes raw Excel files and produces a structured Asana task hierarchy — with stock-checked, routed line items — before a single task is written to Asana.

Stage 1

BOM Consolidation

Merges multi-vendor xlsx files. Enforces Cost Centre column. Normalises part numbers.

Stage 2

Golden Index Match

Strips job prefix, fuzzy-matches to Golden Index Rev4. Assigns KAN numbers where known.

Stage 3

Live Stock Check

Queries KANBAN project in Asana. Compares required qty vs. available. Flags ORDER vs. PICK.

Stage 4 — HITL ✋

Staging Review

Exports Excel for Giles. He adds SKIP, HOLD, FORCE_ORDER, or qty overrides. Only checkpoint.

Stage 5

Asana Import

Creates full task hierarchy in Build Orders project. Embeds Dropbox URL, project refs.

Task hierarchy produced:  ALL BOMS — {project} → PICKING BOM + {CostCentre} BOM → {Vendor} → {qty} off {part} — {desc}

The Golden Index — Part Matching Intelligence

✅ Live (Rev4)
Built

Curated Part Number → KAN Number Lookup

The Golden Index (Merged_Golden_Index_Rev4.csv) is the authoritative mapping between vendor part numbers (prefix-stripped) and Sesame KANBAN stock items. Without it, every BOM import would route every part to ORDER regardless of available stock.

▸
16 columns including Stock_Number, Mapped_KAN, Asana_Name, Confidence, Match_Type, Provisional
▸
Fuzzy matching via SequenceMatcher at 80% threshold — handles minor part number variants
▸
Feedback loop: when Giles confirms a new mapping at Stage 4, it's written back via update_golden_index.py
▸
Two copies must stay in sync — skill folder + OneDrive lab copy
▸
Known gap: the feedback write-back is currently a manual step, not auto-captured from Stage 4 approvals

Purchasing Intelligence Pipeline

✅ Live (ops_agent / SAO)
Built

4-Layer LLM + Human-in-the-Loop Email Parsing

Inbound purchasing emails and supplier PDFs are automatically ingested, parsed by an LLM, matched to Asana tasks, and queued for human approval before any Asana write occurs.

▸
Layer 1: Email fetcher reads purchasing@sesameaccess.com via Microsoft Graph API
▸
Layer 2: LLM parser (Gemini) extracts PO numbers, prices, dates, vendor info, delivery notes
▸
Layer 3: Proposal engine matches against Asana tasks and ops.db, generates pending_approval_queue.json
▸
Layer 3.5 HITL: Commander Claw presents proposals to Giles — approve, modify, hold, or reject
▸
Layer 4: Asana Executor writes approved updates, categorises emails in Outlook, sends receipts
▸
PDF extraction: pdfplumber handles delivery notes, despatch notes, order acknowledgements

After Stage 5, Giles manually adds the imported BOM tasks to the specific job/manufacturing project. This is the last manual step in the import flow. Automating it would require reliable per-job GID resolution, which currently depends on Giles providing the URL at run time.
