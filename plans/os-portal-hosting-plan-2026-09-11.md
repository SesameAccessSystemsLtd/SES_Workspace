# OS Portal Hosting — Plan (staged 2026-09-11)

**Status:** PROPOSED — review with Giles Monday. No VPS/network changes made yet.
**Goal:** serve the SES OS Portal (static dashboards from `ops.db`) as a live portal on the VPS,
behind Cloudflare, reusing the existing Traefik front door already proven for the Asana webhook.

---

## 1. Current verified architecture (VPS `191.215.40.116`, ssh alias `vps`)

```
Internet ──▶ Cloudflare (DNS, orange-cloud) ──▶ VPS :443 ──▶ Traefik (Let's Encrypt)
                                                             ├── router Host(`hooks.sesameaccess.com`)
                                                             │     └──▶ Asana webhook receiver v2 (127.0.0.1 / bridge:8099)
                                                             └── (NEW) router Host(`os.sesameaccess.com`)
                                                                   └──▶ static portal server ──▶ portal HTML
```

- Front door = **Traefik** (`traefik-traefik-1`), dynamic file provider at `/docker/traefik/dynamic/*.yml`,
  `file.watch=true` → **hot-reload, no restart**.
- TLS = Let's Encrypt (LE cert for hooks.* expires 10 Dec 2026). A new host needs its own LE cert
  (HTTP-01 via Traefik — automatic once DNS points at the VPS).
- ufw: 22, 80, 443 open. Receiver listens loopback/bridge only — never exposed directly.
- Pattern to copy: `/docker/traefik/dynamic/hooks.yml` (router + service + tls certResolver).

## 2. NEW pieces required (two only)

### 2a. Static portal server on the VPS
Serve a **curated** copy of the portal (NOT the raw `os_status/` — that has 22+ dated archives + a
550 KB `.hier_cache.json` we must not expose).

Recommended: a tiny container, host-networked, loopback-bound, e.g.:
```
# /opt/ses/portal/docker-compose.yml
services:
  portal:
    image: nginx:alpine
    network_mode: host          # so Traefik (host netns) can reach it on 127.0.0.1
    volumes:
      - /opt/ses/workspace/data/os_portal:/usr/share/nginx/html:ro
    # nginx listens :8080 (edit default.conf) — 127.0.0.1 only
```
Alternatives: `caddy file-server`, or a systemd `python -m http.server` (like the v1 receiver did).

### 2b. Traefik route `/docker/traefik/dynamic/portal.yml`
```yaml
http:
  routers:
    portal:
      rule: "Host(`os.sesameaccess.com`)"
      entryPoints: [websecure]
      service: portal-svc
      tls:
        certResolver: letsencrypt
    portal-http:
      rule: "Host(`os.sesameaccess.com`)"
      entryPoints: [web]
      service: portal-svc
  services:
    portal-svc:
      loadBalancer:
        servers:
          - url: "http://127.0.0.1:8080"
```
(If the container is on a bridge IP like the receiver, add a route-sync timer as `sas-hooks-route-sync`
does — or just run host-networked to avoid that.)

## 3. DNS + Cloudflare Access (the IP login Giles wants)

1. **DNS:** add `os.sesameaccess.com` → VPS IP, **orange-cloud (proxied)** in Cloudflare.
2. **Cloudflare Access** application on `os.sesameaccess.com` with **two policies**:
   - **Policy A — "Office"**: allow by **IP-allowlist** (SES local/office egress IP). Zero login in-office.
   - **Policy B — "Giles remote"**: allow by **email OTP / SSO** for Giles's address.
   This is the "best of both": no password in office, still reachable remotely. IP-only would lock
   out mobile/remote (Giles's own concern) — hence the email fallback policy.
3. (Optional) Cloudflare **WAF** rules + rate limiting on the hostname.

## 4. ⚠️ Critical unknown — LIVE-ness
**Where do the OS-portal refresh jobs run?** Locally (this Windows machine) or on the VPS?
- The portal HTML is generated by cron jobs (Status Snapshot / BOM Tracker / Ops Oversight / Orders by Pack)
  from `ops.db`. On this machine they live in `~/AppData/Local/hermes/cron/jobs.json`.
- The VPS has its own Hermes (`hermes-gateway` container) with its own cron. **If the refresh jobs do
  NOT run on the VPS, a VPS-hosted portal would be STALE** (frozen at last sync).
- **Action Monday:** confirm which host owns the portal-refresh cron. If local-only, either (a) run the
  refresh jobs on the VPS too, or (b) push the locally-generated HTML to the VPS on a schedule.
